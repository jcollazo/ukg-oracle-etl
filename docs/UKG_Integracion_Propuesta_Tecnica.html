1. Resumen Ejecutivo

Con el contrato de UKG/Kronos firmado, se ha iniciado la etapa de diseño de las integraciones del segmento HCM. UKG propone un modelo de una integración por tenant (un archivo por agencia), con reconstrucción del layout por cada tenant. Ese enfoque puede inflar significativamente los costos, el tiempo de desarrollo y el alcance del proyecto.

Este documento propone que OGP asuma el diseño y construcción de la integración con su equipo técnico, utilizando un pipeline ETL propio que recibe un único archivo CSV estándar desde UKG Pro y lo procesa hacia SQL Server. Este enfoque:

  • Elimina la dependencia del modelo per-tenant de UKG.
  • Mantiene el estándar de integraciones mínimas establecido por Deloitte.
  • Reduce costos recurrentes (sin Boomi, sin licencias adicionales).
  • Ofrece control total sobre seguridad, encriptación y auditoría.
  • Cumple con la Ley 126-2012 de Firma Electrónica del Gobierno de Puerto Rico.

2. Arquitectura Propuesta

La integración sigue un modelo SFTP Push + Python ETL + SQL Server Staging con MERGE atómico. El diseño minimiza la carga en memoria (~15 MB RAM) y garantiza resiliencia ante fallos.

4. Seguridad y Compliance Legal

4.1 Encriptación AES-256-GCM (SSN)

El Social Security Number (SSN) se encripta en la capa de aplicación ANTES de que cualquier dato toque la base de datos. El texto plano del SSN nunca existe en staging ni en las tablas destino — solo ciphertext en formato base64.

EtapaSSNProtección
CSV entrante (SFTP)583-12-3456 (plaintext)TLS 1.3 en tránsito
Python (encrypt)AES-256-GCM → ciphertextNonce aleatorio 96-bit
Staging (INSERT)base64(ciphertext) ~88 charsNunca plaintext en DB
MERGE (pass-through)Ciphertext → tablas destinoSin desencriptar
Logs y auditoríaXXX-XX-1234Solo últimos 4 dígitos
Dead letter queueSSN enmascaradoSin plaintext ni ciphertext

4.2 Ley 126-2012 — Firma Electrónica

  • Cada batch de importación genera un hash SHA-256 que encadena todas las filas procesadas.
  • El hash chain se almacena en dbo.ukg_import_log y permite verificar que los datos no fueron alterados.
  • Non-repudiation: el hash prueba integridad criptográfica post-importación.
  • MERGE atómico con XACT_ABORT ON: cualquier error → rollback total de la transacción.

4.3 Otras Consideraciones

  • Credenciales de base de datos vía variables de entorno (nunca en código).
  • Llave de encriptación AES-256 en UKG_ENCRYPTION_KEY (secrets manager).
  • Conexión SQL Server con ODBC Driver 18 + TLS (Encrypt=yes en producción).
  • Data residency: todos los datos residen en servidores on-premise del Gobierno de Puerto Rico.

7. Modelo de Acceso Read-Only para Agencias

7.1 Filosofía: Las agencias leen, no escriben

A diferencia del modelo tradicional de integración — donde cada agencia recibe una copia de los datos en su propia base de datos local (requiriendo INSERT, UPDATE, DELETE) — nuestro modelo read-only garantiza que las agencias solo puedan consultar datos, nunca modificarlos.

Esto simplifica la arquitectura, elimina la necesidad de bases de datos locales en cada agencia, y reduce la superficie de ataque:

  • La agencia NO necesita SQL Server local.
  • La agencia NO tiene permisos de escritura (INSERT/UPDATE/DELETE).
  • La agencia NO instala middleware ni runtimes.
  • Una sola fuente de verdad: SQL Server central en OGP.

7.2 Opciones de Acceso Read-Only

Opción A — Connection String Read-Only (Directo a DB)

#PasoResponsableDetalle
1Crear login por agenciaOGPCREATE LOGIN agencia_xxx WITH PASSWORD='***'
2Otorgar SELECT únicamenteOGPGRANT SELECT ON empleados, agencias TO agencia_xxx

Opción B — API REST (Más Seguro, Sin Acceso Directo a DB)

#PasoResponsableDetalle
1Registrar agencia en el HubOGPPOST /api/agencies → genera API key
2Entregar API key + endpointOGPGET https://hub.pr.gov/api/data/empleados
3App de la agencia consumeAgenciaHTTP GET con Authorization: Bearer <api-key>
4Rate limiting por agenciaHub100 req/min por API key

Opción B es la recomendada: la agencia nunca tiene acceso directo a la base de datos. Solo consume datos vía API REST autenticada con API key. Rate limiting previene abuso. Logs de acceso por agencia habilitan auditoría completa.

7.3 ¿Qué Hace Boomi en Este Escenario?

Boomi opera bajo un modelo fundamentalmente distinto. Su modo por defecto requiere INSERT, UPDATE, DELETE en las bases de datos destino:

Operación BoomiPermiso RequeridoRiesgo
Database Connector — InsertINSERTEscritura no autorizada
Database Connector — UpdateUPDATEModificación de datos
Database Connector — DeleteDELETEEliminación de datos
Database Connector — UpsertINSERT + UPDATEInserción/modificación silenciosa

Fuente: Boomi Documentation — "Database connector: Use to select, insert, update, and delete records in a database."

Para lograr un modelo read-only, Boomi requeriría su producto adicional Boomi Data Hub:

  • Boomi Data Hub es un producto APARTE del Boomi Integration básico.
  • Expone datos vía APIs REST para consumo externo.
  • Requiere licencia adicional y configuración de modelos de datos maestros.
